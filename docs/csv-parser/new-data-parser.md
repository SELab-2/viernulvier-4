# New Structured CSV Parser

This page describes the structured CSV parser: how to use it, how it works, template layout, and restrictions.

## Purpose

The structured parser is the supported CSV import flow for explicit data imports of:

- productions
- events
- tags
- blogs
- prices

It is implemented with dedicated import functions and parser endpoints.

## API endpoints

Implemented in `ParserController`:

- `POST /parser/productions`
- `POST /parser/events`
- `POST /parser/tags`
- `POST /parser/blogs`
- `POST /parser/prices`

All endpoints require `x-api-key`.

Each endpoint accepts either:

- multipart upload (`file`), or
- an internal fallback source parameter used by backend tooling

If both are present, uploaded file is used.

## Required Import Order

Run imports in this order:

1. productions
2. events
3. tags
4. blogs
5. prices

Reason:

- events reference productions via legacy id of production
- tags/blogs link to productions via legacy id of production
- prices link to events via legacy id of event

## How the Structured Parser Works

The parse pipeline is shared across entities through `CSVFileParser.parseCSVWithSchema(...)`:

1. Read CSV input from request/script input.
2. Parse with `csv-parser` in strict mode.
3. Trim header and value whitespace.
4. Transform row into DTO shape.
5. Validate with Zod schema.
6. Skip invalid rows and continue.

Entity-specific transforms are named as follows:

- `transform{Entity}Row`

Then injection functions convert parsed rows into DB-layer entities and create links.

## Design Choices for CSV Separation

### Why separate CSVs?

Events and productions require an ID to link locations, tags, prices, and blogs to them. When imported, these entities receive autogenerated database IDs, but their original CSV ID is stored in `legacy_id` as `csv-{ID}`. This allows later CSV files to reference them by their original ID.

**Prices** have a separate CSV file because they contain multiple fields with NL/EN translations. Including them in the events file would create messy duplication and increase the chance of human error.

**Tags** have a separate CSV file for three important reasons:

1. It enables adding batches of tags and linking them to multiple productions at once.
2. Tags can be added after productions are imported, rather than requiring them to be coupled at import time.
3. Putting tags in the productions CSV would create clutter and high risk of mistranslation or ordering errors in list-based text.

**Blogs** have a separate CSV file to keep them decoupled from production data, making it easy to add or update blogs independently.

!!! warning "Important: ID References"
For proper linking to work, all IDs referenced in tags, blogs, prices, and events CSVs must use the legacy IDs (`csv-{ID}`) from previously imported productions and events. Using any other ID or making up new IDs will cause linking to fail silently.

## Templates, Examples, and Field Nullability

This section showcases the complete template headers, example rows, and field nullability for each CSV type (productions, events, tags, blogs, prices).

### Productions

**Template header:**

```
ID,Titel_NL,Titel_EN,Description1_NL,Description1_EN,Description2_NL,Description2_EN,Artist_NL,Artist_EN,Tagline_NL,Tagline_EN,Credits_NL,Credits_EN,Performer_Type,Attendance_Mode
```

**Example row:**

```
101,De Storm,The Storm,Een muziektheaterstuk,A music theatre piece,Extra info,Extra info,Ensemble Echo,Ensemble Echo,Rauw en dichtbij,Raw and close,Regie Team,Direction Team,actors,offline
```

**Field nullability:**

| Field             | Required | Notes                                     |
| ----------------- | -------- | ----------------------------------------- |
| `ID`              | Yes      | Must be numeric                           |
| `Titel_NL`        | Yes      |                                           |
| `Titel_EN`        | No       | Will be translated if empty               |
| `Description1_NL` | Yes      |                                           |
| `Description1_EN` | No       | Will be translated if empty               |
| `Description2_NL` | No       | Can be empty                              |
| `Description2_EN` | No       | Will be translated if empty and NL exists |
| `Artist_NL`       | No       | Can be empty                              |
| `Artist_EN`       | No       | Will be translated if empty and NL exists |
| `Tagline_NL`      | No       | Can be empty                              |
| `Tagline_EN`      | No       | Will be translated if empty and NL exists |
| `Credits_NL`      | No       | Can be empty                              |
| `Credits_EN`      | No       | Will be translated if empty and NL exists |
| `Performer_Type`  | No       | Can be empty                              |
| `Attendance_Mode` | No       | Can be empty                              |

### Events

**Template header:**

```
ID,Starttime,Endtime,Doors_At,Intermission_At,Location_NL,Location_EN,Production
```

**Example row:**

```
201,2026-04-10 20:00:00,2026-04-10 22:00:00,2026-04-10 18:00:00,2026-04-10 21:00:00,Grote Zaal,Main Hall,101
```

**Field nullability:**

| Field             | Required | Notes                                     |
| ----------------- | -------- | ----------------------------------------- |
| `ID`              | Yes      | Must be numeric                           |
| `Starttime`       | Yes      | Must be valid datetime                    |
| `Endtime`         | No       | Invalid dates are treated as empty        |
| `Doors_At`        | No       | Can be empty                              |
| `Intermission_At` | No       | Can be empty                              |
| `Location_NL`     | No       | Can be empty                              |
| `Location_EN`     | No       | Will be translated if empty and NL exists |
| `Production`      | Yes      | Must reference a production ID like `101` |

### Tags

**Template header:**

```
TagName_NL,TagName_EN,ProductionIDs
```

**Example row:**

```
Muziek,Music,"101,102"
```

**Field nullability:**

| Field           | Required | Notes                                                   |
| --------------- | -------- | ------------------------------------------------------- |
| `TagName_NL`    | Yes      |                                                         |
| `TagName_EN`    | No       | Will be translated if empty                             |
| `ProductionIDs` | Yes      | Comma-separated list of production IDs; each must exist |

**Template header:**

```
Titel_NL,Titel_EN,Description_NL,Description_EN,ProductionID
```

**Example row:**

```
Achter de schermen,Behind the scenes,Korte blik op de repetities,A short look at rehearsals,101
```

**Field nullability:**

| Field            | Required | Notes                                     |
| ---------------- | -------- | ----------------------------------------- |
| `Titel_NL`       | Yes      |                                           |
| `Titel_EN`       | No       | Will be translated if empty               |
| `Description_NL` | Yes      |                                           |
| `Description_EN` | No       | Will be translated if empty               |
| `ProductionID`   | Yes      | Must reference a production ID like `101` |

### Prices

**Template header:**

```
Name_NL,Name_EN,Price,EventID
```

**Example row:**

```

```

**Field nullability:**

| Field     | Required | Notes                                 |
| --------- | -------- | ------------------------------------- |
| `Name_NL` | Yes      |                                       |
| `Name_EN` | No       | Will be translated if empty           |

| `EventID` | Yes      | Must reference an event ID like `201` |

## Field Rules and Restrictions

### General

- IDs and references must be numeric where expected.
- Invalid rows are skipped; import continues for valid rows.
- Legacy IDs are generated as `csv-<id>` for imported records.

### Localization

- Most text fields use NL/EN objects.
- For many fields, NL is required while EN can be empty.
- If EN is empty and NL exists, EN may later be filled by translation flow.

### Linking restrictions

- Tags/blogs referencing unknown productions are skipped with warning logs.
- Prices referencing unknown events are skipped with warning logs.

### API upload restrictions

Accepted MIME types for file upload:

- `text/csv`
- `application/csv`
- `application/vnd.ms-excel`
- `text/plain`

Any other MIME type is rejected.

## Minimal Usage Examples

### Upload file example

```bash
curl -X POST http://localhost:3000/parser/productions \
  -H "x-api-key: YOUR_API_KEY" \
  -F "file=@productions.csv;type=text/csv"
```

## Practical Checklist

- Use template headers exactly for each entity file.
- Import in the required order.
- Ensure referenced production/event IDs already exist.
- Provide `x-api-key`.
- If translation is needed, set `TRANSLATE_API_KEY`.
